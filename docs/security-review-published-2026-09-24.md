## 安全发现

以下源码位置均以审查提交为准，本地工作区存在未提交修改，行号可能不同。

### P1（有前提）：管理工具缺少设备端独立授权边界，继承自上游

证据：`main/mcp_server.cc:525` 仅在工具列表中过滤 `user_only()`；`DoToolCall()` 的第 564–618 行按工具名查找并执行，没有对管理身份进行校验。`self.reboot` 位于第 132 行，`self.upgrade_firmware` 位于第 145 行，后者接受调用方提供的固件 URL。应用注册并接收这些工具请求。

攻击前提：攻击者控制后端 MCP 消息、成功向设备会话注入消息，或者后端错误放行模型发起的管理调用。当前权限安全完全依赖可信后端隔离。可能影响包括重启、启用截图能力时的屏幕上传，以及在缺乏签名校验时替换固件。

关联 OTA 边界：`main/ota.cc:287` 打开传入的固件 URL，第 380、390 行调用 SDK 校验镜像并切换启动分区。根配置没有强制开启签名验证；实际烧录配置和 eFuse 状态未核验。默认 OTA 元数据地址是 HTTPS（`main/Kconfig.projbuild:5`）。HTTP 固件 URL、后端失陷和缺少签名校验会扩大影响。

建议：在工具执行入口验证独立管理授权或要求设备端确认，将管理能力与普通对话分离；升级采用可信发布者签名校验，并限制下载来源和传输方式。涉及 eFuse 的操作需要单独制定恢复方案。

### P2：UDP 音频缺少消息认证，可破坏会话接收序号，继承自上游

证据：`main/protocols/mqtt_protocol.cc:334` 拒绝旧序号，第 339–342 行对跳跃序号仅告警；第 353 行执行 AES-CTR 解密，第 363 行接受并更新 `remote_sequence_`。`CryptAesCtr()` 第 515–535 行检查运算成功与长度，没有认证标签/MAC。

攻击前提：能够向活动 UDP 会话注入通过底层 socket 来源限制的数据包，例如处于链路上或能伪造服务端来源。构造长度合法、序号极大的密文包即可通过 CTR 运算，不需要知道密钥；此后正常序号会被丢弃，导致当前会话音频拒绝服务，直到重建会话。该结论基于代码路径，未发送真实攻击数据包。

建议：与服务端共同升级协议，用 AEAD 或加密后认证覆盖头部和音频内容；认证通过后更新防重放状态。序号窗口可作为额外约束。

### P2：字幕播放新增非原子变量的跨线程读写

证据：`main/audio/audio_service.cc:340` 释放 `audio_queue_mutex_`，第 353 行读取 `playback_generation_`；`ResetDecoder()` 第 809–810 行在另一任务持锁递增，`Stop()` 也会递增。`main/audio/audio_service.h:199` 将其声明为普通 `uint32_t`。

触发条件：字幕播放时发生并发打断、停止或解码器重置。构成 C++ 数据竞争和未定义行为，可能使过期字幕进度被接受或导致不稳定；本次没有验证远程代码执行能力。

建议：统一通过同一把锁访问或采用合适的原子同步，并保证代次检查与进度事件失效逻辑一致。补充打断和停止期间的并发验证。

### P2/P3：仓库保护与供应链检查不足

GitHub API 证据：`main` 未配置经典分支保护；rulesets 列表为空；Dependabot 漏洞告警关闭，安全更新关闭。Actions 允许所有来源，未要求完整 SHA 固定。`.github/workflows/build.yml` 使用 `actions/checkout@v7`、`actions/upload-artifact@v7` 和带标签的 ESP-IDF 容器镜像。

现有正向约束：工作流令牌默认为只读，不能批准 PR；仓库密钥扫描和推送保护已开启。本次没有发现被利用或依赖失陷的证据。

建议：保护默认分支、对新增提交配置密钥检查、启用适用依赖的漏洞告警；将 Actions 固定到经核验的完整 SHA、容器固定到摘要。ESP-IDF 组件依赖需要单独纳入版本与漏洞检查，不能仅依赖 GitHub 开关。
